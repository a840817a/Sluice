# Segment URLs name their period

A segment URL is `/v1/channels/{channel}/segments/{period}/{representation}/{number}{ext}` and an init URL is `/v1/channels/{channel}/init/{period}/{representation}.mp4`. Before this, neither carried the period. When the origin restarts its numbering, the channel starts a new period and reuses segment numbers under the same representation (a multi-period DASH source can do the same), so two periods held the same (representation, number). The lookup walked a Go map and returned whichever period came first, and the HLS media playlist merged all periods by number. A player got the wrong period's segment or init, and after a reset the live playlist stayed on the old period's tail. We chose to put the period in the URL over gateway-assigned numbering that would have kept the URL shape. That alternative would have changed ingest's restart detection, the AES-128 IV and DASH `startNumber`.

## Consequences

- The period-less routes were removed rather than kept as a fallback, so every segment and init URL cached by a player or CDN before the upgrade returns 404. A live player recovers by reloading its playlist.
- A period ID made only of letters, digits, `.`, `_` and `-` goes into the URL as is. Any other ID, including the empty ID of a DASH period with no `id`, and `.` and `..`, is written `~` followed by unpadded base64url (`pathseg.Encode`). Percent-encoding was rejected because the router hands the handler either the escaped or the decoded segment, depending on how the request path happened to be escaped.
- Amended 2026-10-14: a representation ID was left raw, so an ID containing `/` (Bento4 mp4dash names representations `video/avc1`) spread over several path segments and every URL for it returned 404. A representation ID now goes in as is unless its raw form cannot be one path segment: one containing `/`, `\`, `?`, `#` or `%`, the empty ID, `.`, `..` and an ID starting with `~` are written in the same `~` and base64url form (`gwurl.ParseRepSegment` reverses it). This is looser than the period rule on purpose: representation IDs were in URLs before either encoding existed, and IDs such as `audio=128000` keep the URLs players and CDNs hold. The init and media playlist routes take the whole segment and strip `.mp4` or `.m3u8` in the handler, because chi ends a `{repID}.mp4` parameter at the first `.` and an ID like `mp4a.40.2` never matched.
- Periods are laid out in one order everywhere (`index.OrderPeriodIDs`): a DASH source's MPD document order, HLS period numbers numerically.
- The HLS media playlist emits `EXT-X-DISCONTINUITY` and a fresh `EXT-X-MAP` at each period boundary. `EXT-X-DISCONTINUITY-SEQUENCE` counts every discontinuity that has left the window: the period boundaries, and the origin discontinuities inside a period, whose segment numbers each representation keeps in memory like its lifetime range (below). A discontinuity on a period's first segment is that period's boundary and counts once. After a restart the record is recomputed from disk, so if old segments were cleaned up the value shifts once.
- Media sequence numbers are derived, not stored. A period is numbered after the previous period's highest segment number, from each representation's lifetime range of published segments, which the index keeps in memory. A segment committed but never published is left out of that range: it is in no playlist, and counting it would open a gap in the numbering that cuts the playlist at the period boundary. The range only ever grows, so it does not move as the live window slides. After a restart it is recomputed from disk, and if an old period's files were cleaned up the numbering shifts once, making live players reload.
